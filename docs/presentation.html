experimental v0

a11yFixer

One Jira ticket with 12 subtasks in.
12 small, independent, reviewable draft pull requests out.

~2,000 lines · Node + TypeScript · no dependencies · built in an afternoon

the problem

One big agent, twelve tickets

What everybody tries first.

ticket 1 ✅ good ticket 2 ✅ good ticket 3 🙂 ok ticket 4 😐 hmm ticket 5 😵 confused ticket 6 💀 nonsense

Its memory fills up. Decisions from ticket 2 leak into ticket 7.

And at the end you get one enormous pull request touching everything, that nobody wants to review.

the idea

A foreman who hires a new contractor for every job

The foreman is deliberately ignorant. He doesn't know how to do the work, and he doesn't know the house rules.

  1. Builds a brand new empty workshop — a clean copy of the codebase
  2. Hires a contractor, who first reads the house rulebook lying in the workshop
  3. Contractor does that one job only, then goes home
  4. The foreman runs the inspection himself — he never asks "did it go well?"
  5. A second inspector who never met the contractor sees only the finished work
  6. If it passes, he files paperwork as a draft for a human to sign
  7. Then he burns the notes. Next job, new contractor, remembers nothing

the interface

You type one line

npm run a11y-fixer -- \ https://user-testing.atlassian.net/browse/RAD-85350 \ --repo ~/results/frontends/microfrontends
A parent Jira ticket, and the repo to work in. That's it. Everything else it figures out for itself.

step 0 · before anything else

Prove it can talk to Jira

🔑 Jira connection OK 31s read ✔ mcp__claude_ai_Atlassian__getJiraIssue RAD-85350 — Deque Audit: Apply video player accessibility fixes write ✔ Paweł Stanecki transitions: In Planning, Ready To Start, In Progress, … Done
Thirty seconds to prove I can read Jira and write to Jira. If my setup is broken I find out now — not after half an hour of work.

The tick only appears if the ticket's title actually came back. An agent saying "yes I'm connected" is not accepted.

step 1 · discovery

Ask Jira what the jobs actually are

It only takes the ticket's real children. Linked tickets, "relates to", blockers — deliberately ignored.

Follow the links and the scope explodes. One ticket becomes forty. The whole point is small.

the shape of the work

Every branch starts from the same frozen commit

parallel — never stacked

Ticket 2's changes are never in ticket 3's pull request.

Each PR contains one ticket's worth of change, so a reviewer can actually hold it in their head. That only works because nothing builds on top of anything else.

One repair attempt. One. No infinite loops — if it can't fix it, it fails honestly and moves on to the next ticket.

the clever bit

The reviewer has never met the builder

If the reviewer could see the builder's justification, it would just be marking its own homework.

It gets the ticket, the diff, the repo's standards and the test results — and forms its own opinion from scratch.

MANUAL_REVIEW_REQUIRED isn't a failure. Accessibility often genuinely needs a human with a screen reader. That verdict still ships a draft PR — it just says so in the description.

the design rule

Three jobs, kept strictly apart

a11yFixer

knows the process

Make a workshop. Run the tests. Commit. Push. Open a draft PR. Never what to write.

your repo

knows the policy

Branch names, commit style, which tests, PR template, accessibility standards. Lives in AGENTS.md — not in my code.

the agent

interprets the policy

Reads the repo, works out what the rules mean for this ticket, and follows them.

There is not one line in a11yFixer that knows how UserTesting names branches or runs tests. That's why it would work on your repo tomorrow.

the bug that shaped everything

It built a whole pull request without ever reading the ticket

  1. I have ~350 tools connected, so Claude Code hides them behind a search
  2. The agent searched for "jira atlassian" — and got nothing back
  3. So it concluded Jira didn't exist… and carried on anyway
  4. It implemented from the ticket title, opened a PR, and reported no problem at all
The failure wasn't the AI being stupid. It was my harness trusting a self-report.

the fix · and the rule it created

Prove it. Never claim it.

Ask for a tool by exact name, never by fuzzy search:

ToolSearch("select:mcp__claude_ai_Atlassian__getJiraIssue")

Fetch the ticket once, to a file. Every later agent reads that file.

artifacts/RAD-85351.jira.md

"Did it actually read the ticket?" is now answerable by opening a file.

nothing passes on its own say-so

Jira read — only if the ticket's title actually came back

Jira write — only if a real account ID actually came back

Ticket text — long enough, and mentions the right key

The work — git diff shows files really changed

The verdict — anything unreadable becomes MANUAL_REVIEW, never PASS

deliberately not built

What it refuses to do

Never merges

Every PR is a draft. A human always decides.

Never force-pushes

Only its own new branch, never yours.

Never touches your checkout

All work happens in temp folders.

No shell for the coder

The building agent can edit files but can't run commands. I kept that.

No retry loops

Exactly one repair attempt, then it fails honestly.

Never deletes evidence

Failed attempts stay on disk so I can go and look.

Worst case: a draft pull request I close. That's the whole blast radius.

why it exists

It was built to answer one question

Is parent ticket → isolated agents → real tests → independent review → small draft PRs useful enough to keep investing in?

Answered

It produces real, reviewable pull requests that follow team conventions.

Still open

Is the review verdict trustworthy? Is 30 min & ~$20 per ticket worth it?
